# F2.4 — Execution store implementation plan

Status: proposed; Q-13 is unanswered. This document does not approve a design change or
start implementation. F2.3 merged as PR #38, main commit `9f7fc76`.

Design baseline: base-doc commit `677711730e6fe1aa9bca6bc5719d53755631a702`,
`storage-security` §§2–3, 6 (related payload/retention constraints in §§4, 7), and
`event-storage-recovery` §5 (envelope, admission and transcript contracts in §§3–4, 6).
Repository authority: ADR 0001, roadmap F2.4–F2.6, and quality-gates.

## 1. Outcome and existing decisions

Provide the SQL transaction adapter used by the future coordinator. A successful append
persists one complete transition; a rejected or failed transaction leaves no partial batch.
The adapter never schedules, dispatches, calls a provider/tool, or grants execution authority.

Already decided; do not reopen these choices:

- Local `fugue.db`, modernc SQLite, one shared connection, DELETE journal, synchronous FULL,
  foreign keys enabled, private permissions and exclusive data-directory lock.
- `BEGIN IMMEDIATE`; seal outside the transaction; no network, vault decryption, worker or
  interaction waits while the transaction is held.
- One transaction for sealed payloads, events, projections, transcript, receipt and admission.
- Immutable protected canonical input, direct byte equality and version-aware receipt dedup;
  no plaintext digest, HMAC, external payload files, sync or alternative writer.
- Append-only event/payload triggers, with the session-purge exception in the design.
- Rebuild from events with no effects and no new persisted execution snapshots.
- Unknown commit requires receipt read-back; unreadable database means unavailable, not retry
  authorization. Unrecognized required event/protocol versions also fail closed.

## 2. One actual phasing conflict: Q-13

Sources that cannot both be delivered literally in their current order:

1. Roadmap F2.4 requires an atomic transaction including payloads and append-only triggers.
2. `storage-security` §3 requires triggers over `exec_events` and `exec_payloads` with an
   `exec_purges` exception; §6 inserts sealed payloads before events in the same transaction.
3. ADR 0001 §5 schedules `exec_payloads`, `exec_session_keys` and `exec_purges` for F2.5,
   while roadmap F2.5 depends on F2.4.

This is a delivery/dependency contradiction, not a reason to change the security model.
With the current phase assignments, F2.4 cannot demonstrate its complete stated exit before
its payload storage dependency exists. A plaintext fallback, dangling payload reference or
fake successful payload writer would not resolve it.

### A — Recommended: introduce the physical support tables in F2.4

Move only the schema and sealed-record persistence boundary for the three support tables to
F2.4, along with their constraints and trigger support. Keep their owner `internal/execstore`.
F2.5 retains session-key creation/wrapping/unwrapping, AEAD seal/open, vault guards/cache
zeroing, size limits, purge orchestration and crypto-shred evidence.

F2.4 can atomically persist already sealed records and test atomicity with genuine encrypted
test inputs. These tests establish database atomicity, not complete vault or key-lifecycle
security. Until F2.5 supplies the protected-input preparation/opening path, production
protected commands must fail closed; metadata-only operations can be exercised independently.
Do not treat arbitrary caller bytes or `ExistingInputAvailable` as authenticated vault proof.

Approval requires aligning the phase entries of ADR 0001 and the F2.4/F2.5 roadmap notes.
No ADR or gate-defining file is changed by this planning PR.

### B — Alternative: narrow the F2.4 exit and complete the atomicity proof in F2.5

Leave the support tables in F2.5. F2.4 proves metadata-only event/projection/receipt/admission
atomicity and event immutability. Explicitly move payload insertion, payload triggers, purge
exceptions and the complete protected transition proof to F2.5. F2.4 may not be described as
having completed the current full payload-inclusive exit criterion.

This requires changing the roadmap's milestone boundary and evidence assignments, but does
not waive the final G-03 requirements. Do not silently implement B while claiming A's exit.

## 3. Proposed scope after Q-13

The table below assumes A solely to make the proposal concrete; it is not an approved change.

| Tables / responsibility | F2.4 delivery | Later integration |
| --- | --- | --- |
| `exec_host` | Consume existing host authority through storage APIs; no SQL ownership change | Host composition in F5 |
| `exec_admission` | Session/run identity, revisions, monotonic token, context-control fields; fenced atomic updates | Queue/scheduler/recovery/context-selection handlers in their own items |
| `exec_runs` | Run cursor, revision, version and derived control projections | Later event behavior extends explicit projections |
| `exec_events` | Unique event identity; per-run contiguous sequence; versioned control data and immutable payload refs | No separate stream or snapshots |
| `exec_invocations`, `exec_attempts` | Explicit control projections derived from the accepted event batch | F3 retry/reconciliation handlers remain outside this item |
| `exec_receipts` | Immutable command identity/input binding and exact durable result | Coordinator consumes it in F2.6 |
| `exec_transcript` | Ordered input/selected response/result references and typed dispositions, updated atomically | Context assembly and pruning in F4 |
| `exec_payloads`, `exec_session_keys`, `exec_purges` | Under A: physical schema, sealed-record transaction integration and trigger dependencies | F2.5 supplies cryptographic lifecycle and actual purge operation |
| Timers, time windows, context-decision index, queue, goals | Retain the later phase assignments in ADR 0001 | F2.6, F3.4, F4.5, F5.4, F5.5 respectively |
| Session policy, jail processes | Outside F2.4; do not implement every table merely because its name starts with `exec_` | Their interaction/sandbox owners and designs |

F2.4 does not close all of G-03. In particular, context-chain rebuild, time-window accounting,
crypto-shred, vault-lock races and coordinator dispatch-once evidence remain assigned to their
own milestones. Preserve the relevant event facts now; do not claim those integrations pass.

## 4. Concrete work sequence

### 4.1 — Schema and security boundary inventory

Before writing migration SQL, produce a column-to-source mapping for each in-scope table:
PK/FK/UNIQUE/CHECK rules, nullable states, indexes for actual queries, and allowlisted metadata.
DDL lives only in `internal/storage/migrations`; SQL readers/writers stay with their ADR owner.
Use the next migration number after checking main; do not reserve a number in this plan.

Keep content in sealed records. Do not persist a generic `kernel.State` dump or an arbitrary
JSON blob supplied by a caller. Classify event/receipt fields explicitly; free-form reasons,
`ReceiptResult.Message`, raw errors, prompt/args/output and secrets are not automatically safe
because their Go type is string. Persist fixed codes or protected refs instead.

### 4.2 — Durable record mapping and event codec

Define versioned records covering all currently declared kernel event types. Decode to the
existing typed events and reconstruct state with Evolve and the applicable invariant checks.
Add an exhaustive registry test so adding an event cannot silently omit its storage mapping.

The durable envelope adds event ID, session identity, schema/protocol versions, writer and
executor provenance and correlation where required by the design. These facts come from
trusted host preparation; retain and verify the existing kernel envelope fields. Do not infer
identity from timestamps or accept a model/client origin claim as writer authority.

A separate storage envelope is an implementation choice, not a contradictory design: the
minimal pure `kernel.Envelope` need not become a transport or SQL type. Use injected IDs/time.
Reject unsupported required versions, malformed records and sequence gaps; never skip them
and run from a stale projection. Fuzz the new decoder.

### 4.3 — Store boundary and transaction writer

Design a concrete store API around these operations (names are provisional):

| Operation | Inputs / result |
| --- | --- |
| Append transition | Trusted prepared batch, run/session identity, expected revisions, admission or queue fence, immutable sealed records and receipt result |
| Read run | Consistent projection plus cursor; no protected content in diagnostics |
| Read events | Ordered versioned records for validated replay; reject gaps/corruption |
| Lookup receipt | Existing command binding/result, or explicit not-found |
| Resolve uncertain commit | Verified connection reacquisition plus receipt lookup; committed/not-committed/unavailable |
| Rebuild projections | Fold event history without dispatch; verify against normal projection writes |

Keep interfaces at real consumer boundaries. F2.6 defines its coordinator-facing port in
kernel types per ADR 0001; F2.4 must not add an alternate coordinator or create placeholder
packages merely to host an interface. Keep database, crypto and codec records out of the
future consumer port via explicit adapters as needed.

Use a dedicated connection for BEGIN IMMEDIATE and all SQL through that same transaction.
Recheck admission/run/session revisions inside it, append the whole batch, write projections,
transcript and receipt, and update admission. Check affected-row counts on CAS operations.
Queued commands must not acquire/clear another run's admission. Reject identity mismatches,
invalid sequence/ranges and signed-int64 storage overflow before writing.

Durable results distinguish applied batch, successful no-op and typed semantic rejection.
Document their empty event-range encoding; do not encode disposition in free-form messages.
Infrastructure errors are not fabricated successful receipts.

### 4.4 — Dedup and unknown commit

Prepare protected equality reads outside the SQL transaction. Inside it, re-read the receipt
and verify that its immutable identity/input reference still matches the prepared comparison.
If a receipt appeared or its binding differs from the preflight read, roll back and repeat
preparation outside the transaction. No decryption while holding the database transaction.

Same command binding/content/version returns the original result without another append.
Different kind/principal/target/content/version returns the appropriate typed conflict.
Metadata-only commands use only the explicit safe field allowlist. Protected-input equality
that cannot be established fails closed. The F2.5 vault integration must establish current
owner validity; a preflight snapshot alone is not a proof of authority at commit.

After an ambiguous COMMIT, do not append again or dispatch. Reacquire a verified physical
connection under the existing data-directory lock and read the command receipt. An observed
receipt means committed; a readable DB with no receipt means not committed. If reopening or
reading fails, remain unavailable. Do not close the shared `sql.DB` behind vault/credentials;
connection recovery must respect the shared handle and storage ownership.

F2.4 proves this persistence classification. F2.6 proves that the coordinator obeys it before
handoff; F2.4 tests must not claim dispatch-once behavior for a nonexistent coordinator.

### 4.5 — Fault injection, rebuild and review

Name fault points after payload insert, event append, each projection/transcript phase,
receipt insertion, admission update, and before/after COMMIT. Cover both rollback errors and
real subprocess termination/reopen with on-disk SQLite. A transaction-method stub alone is
not crash durability evidence.

Use a narrow commit-boundary fault adapter to simulate a successful COMMIT whose acknowledgement
is lost, an uncommitted failure, and an unreadable DB. Never add a production bypass around
fences, triggers, vault checks or commit-before-dispatch.

## 5. Acceptance evidence to implement

Names below are planned tests, not claims that evidence already exists.

| Evidence test | Required observation |
| --- | --- |
| `TestExecutionStoreRejectsUnsafePragmas` | FULL/DELETE required on initial and recovered connection |
| `TestExecutionMigrationConstraints` | PK/FK/unique/version constraints hold; migration idempotent |
| `TestExecutionBatchAtomicAcrossReopen` | Injected failure at every write boundary leaves all-or-none rows |
| `TestExecutionCrashRollsBackIncompleteBatch` | Real process exit before COMMIT leaves no partial transition |
| `TestExecutionEventsAndPayloadsAreAppendOnly` | UPDATE/DELETE rejected; unrelated session cannot use a purge exception; payload assertion depends on Q-13 |
| `TestExecutionReceiptSurvivesRestart` | Same canonical invocation returns the exact original result after reopen |
| `TestExecutionReceiptConflictWritesNothing` | Changed content/metadata/version never adds events, receipts or projections |
| `TestExecutionMetadataOnlyDedupNeedsNoPayloadOpen` | Safe metadata-only command path performs no protected input read |
| `TestExecutionProtectedDedupFailsClosed` | Unavailable protected equality cannot authorize a match or append |
| `TestExecutionRejectsStaleFenceAndRevision` | Old admission/queue/run authority cannot write |
| `TestQueuedFinishKeepsOtherRunAdmission` | Queued finish does not clear a different active run |
| `TestExecutionCommitReadBack` | Lost commit acknowledgement and failed commit classified correctly; unreadable DB unavailable |
| `TestExecutionReplayMatchesProjections` | Event fold matches transactional control/transcript projections, without model/tool calls |
| `TestExecutionRejectsUnknownVersionAndSequenceGap` | Incompatible or incomplete history is unavailable, never silently repaired |
| `TestExecutionMetadataContainsNoProtectedContent` | Persisted control columns and diagnostics exclude synthetic protected text |
| `TestExecutionEventCodecCoversKernelRegistry` | Every declared event has a typed versioned storage mapping |
| `FuzzExecutionEventDecode` | Decoder rejects malformed/unsupported data without panic or content leakage |

Require race/shuffle tests, goleak, architecture, full task check, execstore coverage >=90%
and mutation >=85%, plus native Linux/macOS CI. Do not change thresholds, fixtures or gates
to accommodate the plan. Purge/key-zeroing/size-limit/lock-race security proofs remain F2.5.

## 6. Delivery mechanics, not an extra architecture decision

The ~600-line PR guideline and one-item/one-PR rule still apply. F2.4's expected scope is
unlikely to fit a single small PR; this is a planning estimate, not a measured patch size.
Before implementation, obtain a delivery split or a concrete size exception rather than
repeating the unplanned growth of F2.3. A possible sequential split for approval is:

1. Schema/constraints/triggers (after Q-13), with meaningful migration tests.
2. Typed durable records/event codec and compatibility tests.
3. Fenced atomic writer, receipts and transactional projections.
4. Commit read-back, crash/rebuild evidence and complete integration.

These are proposed slices, not newly authorized roadmap IDs. No stacked PRs; each slice
starts after its predecessor merges and must pass all applicable gates. Do not mark F2.4
Done until the full agreed evidence exists and passes. No dependency or gate change is
anticipated for this plan; any later necessary change follows the repository approval rule.

## 7. Review conclusion

Only Q-13 is a confirmed contradiction requiring a milestone/design amendment. Table/column
names, transaction mechanics, storage envelope enrichment, exact typed error representation,
connection reacquisition and explicit field allowlists are implementer-owned details under
already settled contracts. The missing full durable envelope in today's kernel is an
implementation gap, not evidence of incompatible requirements. PR slicing is a delivery
approval, not a second security/architecture conflict.
