**Goal:** One run goes start → model → tool → model → finish through the real coordinator,
execution store, faux provider and `pure_read` tool, producing exactly the 22 events of Trace A
in the 12 transactions of `event-catalog` §7; replaying the stored run makes zero model and
tool calls.

**Architecture:** `internal/app` composes the pieces. A **driver** turns each committed state
into the next mechanical command (dispatch the planned model attempt, run the tool gate,
dispatch a ready tool) — it decides nothing the kernel decides. A **model executor** and a
**tool executor** implement `coordinator.Executor` over `faux.Provider` and `pureread.Tool`,
reporting observations with their payloads. Small **host records** give the kernel the evidence
refs it requires (queue decision, dispatch authorizations, context) as IDs of real sealed
payloads. The coordinator's existing commit notification is promoted to the production
`Config.OnCommitted` hook so the driver hears about every commit.

**Tech Stack:** Go stdlib, `internal/{app,coordinator,execstore,kernel,modeladapter/faux,
tools/pure_read,storage,vault,codec}`, `go-cmp`, `goleak`. No new module.

**Spec:** base-doc `content/projects/dev-kit/core-harness/` at `04163f3` (the named pages are
byte-identical to the `0ec4431` the plan was first written against): `event-catalog` §7

## Global Constraints

- **Every ref the kernel requires is the ID of a real sealed payload** written in the same
  append transaction as the first event that names it (`coordinator.Request.Payloads` through
  `NewCoordinatorStore`, F2.6b), or of one sealed earlier in the same run. Never a constant, a
  generated placeholder, or a ref with nothing behind it. Payload kinds are `[a-z_]+`
  (execstore `isValidKind`).
- Origins: the run's `AcceptRun` is `user` (the test plays the authenticated host layer);
  commands the driver submits are `session`; worker observations are `worker` (set by the
  coordinator). Nothing reads a command's own `Origin`.
- **Command input modes** (execstore allows exactly one per append; `PrepareDispatch` and the
  `Observe*` kinds are not metadata-permitted): `AcceptRun` is metadata-only
  `{"InputRef": "<payload id>"}`; every driver `PrepareDispatch`/`ObserveToolCheck` and every
  executor observation carries `ProtectedInput = codec.MarshalCanonical(command)` (sealed as
  `command_input`). `AdmitRun` and `TimerFired` metadata are built by the coordinator itself.
- The driver never decides continuation, budgets or outcomes; the kernel (F2.9) does.
- No goroutine outside `supervise.Go`; no `time.Sleep`; tests wait on channels and use the
  fake clock; `goleak` in every `TestMain`.
- **Commands:** targeted tests run through `task test-pkg PKG=... [RUN=...] [COUNT=...]`
  (merged as #61), architecture tests through `task arch`; never a bare `go test`.
  `task check` remains the final gate (it bounds its own load).
- Coverage of `internal/app` ≥ 80 %, `internal/coordinator` stays ≥ 90 %; files ≤ 500 lines.
- **ADR change:** ADR 0001's `internal/app` row lists `internal/tools` but `matchPackage` in
  `internal/arch` is exact unless the entry ends in `/...`, so importing
  `internal/tools/pure_read` needs the row to name `internal/tools/...` explicitly. Add it in
  this PR. `docs/adr/**` is **not** a quality-gates §10 gate file: `gate-guard` does not
  require `gate-change-approved` for it; the owner approves through review (CODEOWNERS:
  `/docs/adr/ @syurodev`).
- PR budget ~600 changed non-test lines. Q-29 (A, user, 2026-11-06) splits the estimated ~700
  into F2.10a (Tasks 1–3, ~490: hook ~40, records ~150, executors ~300) and F2.10b (Tasks 4–5,
  ~230 plus tests and the roadmap row). Stop and report if F2.10a goes past about 600.

## Scope decisions made by this plan

1. **Commit hook — replace, not add.** The session already notifies commits internally:
   `notifyCommitted()` fires from `requestCommitted` (session.go), both `dispatchCommitted`
   branches (dispatch.go) and `observationCommitted` (observe.go), and read-back resolutions
   reach the same `done` callbacks (`settle` in commit.go). The admission commit does **not**
   notify today — `admitted` (queue.go) is the one missing call site. F2.10 promotes the
   unexported test field to production API: `Config.OnCommitted func(runID string,
   state *kernel.State)`, called on the actor after every applied commit **including
   admission**; the unexported field is deleted and the two coordinator tests that set it
   (`session_test.go`, `observe_test.go`) set `Config.OnCommitted` before `Start`. One
   mechanism, no `export_test.go` copy: `internal/app` consumes it in production. It must not
   block and must not call back into the session synchronously; the driver enqueues the run ID
   and acts from its own goroutine. `state` is the actor's post-commit snapshot
   (`s.runs[runID]`, folded or reloaded before `done` runs); it is read-only and may be nil if
   the reload failed — the callee must tolerate that. **Snapshot contract:** the coordinator
   never mutates a published `*kernel.State` in place — `kernel.Evolve` is copy-on-write and
   every commit replaces `s.runs[runID]` — so a snapshot stays valid and unchanged after later
   commits (`TestOnCommittedSnapshotIsImmutable` pins this under `-race`: a reader goroutine
   walks the snapshot it received while the session commits the next command; the race
   detector stays clean and the snapshot is unchanged). A lost notification is recoverable: the
   driver can always recompute from `Store.LoadRun` (architecture §3).
2. **Next command is a pure function of state** (`nextCommand`, Task 4): run not admitted,
   finished, waiting or an attempt `Requesting`/`Streaming` → nothing (the coordinator owns
   admission; the executor owns the stream). Model attempt `Planned` → `PrepareDispatch(model)`;
   frontier tool attempt `Planned` → `PrepareDispatch(tool)` (commits `ToolCheckStarted`, hands
   off nothing — `ToolCheckStarted` is not a dispatch event); tool `Checking` → run the gate and
   submit `ObserveToolCheck`; tool `Ready` → `PrepareDispatch(tool)` (real dispatch).
3. **The tool check is a host command.** No worker lease exists for a check
   (`validateObservationLease` needs a dispatched fence), so the driver submits
   `ObserveToolCheck` through `Session.Submit` with origin `session`; the executor only runs
   `Prepare` and returns the check's parts. The kernel pins `GateObservation` to the literal
   `"allowed"` and an empty `ApprovalReceiptRef` (`validateToolCheck`) — there is no gate
   payload ref in Trace A.
4. **Host records.** `queue_item` (session, run) and `queue_decision` (policy
   `admit_when_idle`, version, item ref) — `AcceptRun.QueueItemRef` and
   `Request.QueueDecisionRef`; `model_authorization` (model ref, provider `faux`, no account,
   provider settings, catalog version) — its ID fills `DispatchAuthorizationRef`,
   `ProviderSettingsRef` and `AccountID` of `Facts.ModelDispatch` (the kernel requires all
   three non-empty; one real record behind them); `tool_authorization` (tool, descriptor
   version, `pure_read` class, "no approval required") — its ID fills `Facts.DispatchAuthorizationRef`
   of the tool dispatch (`ToolDispatchStarted.ReceiptRef`). All sealed as payloads. The old
   plan's `tool_gate` record is dropped: no kernel field carries it (decision 3).
5. **Context.** The context engine is F4.5. For F2.10 the context of a step is the canonical
   transcript material so far (input, selected responses, tool results) serialized with
   `codec` as one `context` payload; `ModelRequestPlanned.ContextRef` names it, the model
   executor builds `modeladapter.Request` from it, and the tool executor extends it with the
   tool result for the next step's plan. No summarization, pruning or layering. This slice
   plans exactly one next step: a tool_use response proposing more than one call fails closed
   (`errTooManyToolCalls`); the canonical response record and the context fan-in for
   multi-call steps are Q-30, needed before any real provider (F4.3).
6. **Usage.** `BudgetObserved.TokensUsed = (Input − CacheRead) + Output` from the faux
   `Usage` — reasoning is a subset of output (model-adapter §6), never an addition (budget §4:
   new tokens only); `Basis = "provider_reported"`, `WindowID` empty, `DurationUsed` 0,
   `UsageStatus` `"known"` (`validResponseUsage` bounds and rejects the rest). Negative counts
   or `CacheRead > Input` are the typed failure `errUsageInvalid`, never a negative count.
7. **Failure path (model and tool).** `tool_use`, `stop`, `length`, `refusal` map to the
   kernel `FinishReason` of the same name. On `error`/`aborted`, an unparsable tool-call
   argument, or a payload that fails to seal, the executor's internal execute returns a typed
   error (`errcode` sentinel with a stable code); `Execute` writes **one** `slog` line with
   the lease IDs and the error code only — never payload or plaintext content — and reports
   nothing further. After `Execute` returns the worker always posts one `served(lease)`
   mailbox message, and the actor reclaims the slot with the idempotent `completeSlot`: freed
   exactly once whether the terminal observation committed, was rejected, or was never sent
   (`TestAbandonedWorkFreesTheSlot`, `TestRejectedTerminalObservationFreesTheSlot` at the
   coordinator level). The attempt stays `Requesting` (no events are appended) and nothing
   retries: the driver's `nextCommand` never acts on `Requesting` (F3.3 owns retry).
   `TestModelFailureLeavesAttemptRequestingAndFreesSlot` pins the whole path. Trace A never
   takes these paths.
8. **Tool plans from the stream.** The model executor accumulates `toolcall_*` events into one
   plan per call: `ToolCallID` = stream `CallID`, `SourcePosition` = order,
   `DescriptorVersion` = the host's `pure-read` descriptor version, `EffectClass` =
   `kernel.EffectClassPureRead`, `FirstAttemptID` minted, `InputRef` = a canonical `tool_args`
   payload (the stream's raw `Arguments` string is untrusted model output: parsed strictly
   with `encoding/json`, re-marshalled canonically), `Terminates`/`RepeatsPrevious` false.
9. **Duplicate notifications and a bounded command-ID cache.** The driver derives each
   command ID once per `(runID, state.LastSequence, action)` and caches it, so the same state
   always yields the same command ID and the store's receipt dedup answers a re-delivered
   notification (`checkPreflightDedup` compares Kind/Principal/Target and the protected input
   plaintext — all deterministic; fresh authorization payload IDs never affect it, and the
   dedup runs before any payload row is written). The cache is **bounded**: per run it keeps
   only the IDs of the current `(LastSequence, action)` set — entries of older sequences are
   dropped when the sequence advances, and the run's entry is deleted when the run finishes
   (`TestDriverCommandCacheIsBounded`). A duplicate `PrepareDispatch` reply carries
   `Duplicate: true` and no dispatch event, so the slot is released and nothing is handed off
   twice — the store dedup, not driver bookkeeping, is the no-double-run guard.
10. **Timers (Q-28).** Trace A schedules no timer. `Session.armTimer` no-ops while no
    scheduler is attached (`SetScheduler` is never called by F2.10), so the slice needs no
    timer code at all; the composition-root start after recovery stays F3.1 (roadmap F2.10
    note; event-storage-recovery §7 forbids scheduling before vault catch-up). See Q-28.

## Review Focus

1. **An observation that arrives before the dispatch reply** — the driver must not issue a
   second command for the same step. Pinned in Task 4 (`TestDriverActsOncePerCommittedState`).
2. **A duplicate commit notification** — idempotent: the same state yields the same command
   ID, so the store dedups (decision 9). Pinned in Task 4.
3. **A payload that fails to seal** (vault locked mid-run) — nothing appended, the run waits;
   no plaintext in errors or logs. Pinned in Task 5 (`TestLockedVaultStopsTheSliceWithoutLeaking`).
4. **Tool arguments the model sends that `pure_read` rejects** — the check fails closed, no
   dispatch. Pinned in Task 3 (`TestInvalidToolArgsNeverDispatch`).
5. **Process exit right after the run finishes** — reopen shows 22 events and a finished run;
   nothing replays. Pinned in Task 5 (`TestTraceASurvivesReopenAndReplaysWithoutEffects`).
