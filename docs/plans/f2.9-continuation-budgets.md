# F2.9 — After-step rules and run budgets implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

Status: approved plan, written 2026-11-05 against `main` at `e85474b`. Q-16, Q-17 and Q-18 were
answered by the user on 2026-11-05 (see [§ Decisions](#decisions)). Implementation has not
started.

**Goal:** After every step the kernel decides, deterministically and from recorded facts,
whether the run continues, finishes or waits; the run budgets `steps`, `tokens` and
`tool_calls` make the run wait as `budget(kind)` instead of ending; only the user extends a
budget or ends a waiting run; a `length` answer continues automatically once; consecutive
identical tool calls produce loop reminders at the 3rd, 5th and 8th call.

**Architecture:** All decisions live in `internal/kernel` as pure code. A new pure function
`AfterStep` maps step facts to a continuation reason and is called from the two places that
complete a step today (`responseEvents` in `decide_model.go`, the last tool result in
`decide_tool.go`). Budget counters are folded by `Evolve` from existing events. Facts the
kernel cannot compute (finish reason, steer pending, descriptor `terminate`, "same tool and
canonical args as the previous call") come from the host and are **recorded in events before
they are used**. `internal/execstore` changes only where the codec or the metadata allowlist
must follow the new fields.

**Tech Stack:** Go stdlib, `internal/kernel`, `internal/execstore`, `go-cmp`, `rapid` (tests),
`goleak`. No new module.

**Spec:** base-doc `content/projects/dev-kit/core-harness/` at commit `0ec4431`:
`continuation` §2 (after-step table), §3 (step limit), §4 (loop detection), §6 (events), §8
(evidence CN-E01–CN-E04); `budget` §4 (run budgets), §8 (kernel changes), §9 (BG-E12);
`state-machine` §9 (budgets). Repository authority: roadmap F2.9 and §7 Q-16–Q-18, ADR 0001,
`docs/quality-gates.md`.

## Global Constraints

- `internal/kernel` stays pure (`kernelpure`): no clock, randomness, I/O, goroutines,
  reflection or mutable package state. Every input is a command field or a `DecisionFacts`
  field.
- A host fact that changes a decision is written into the event that uses it, so `Evolve` and
  replay reach the same state without the host (`architecture` §2).
- No tool argument, prompt, hash or fingerprint of either goes into an event or metadata;
  repetition is a host-computed boolean (`event-storage-recovery` §5).
- Default run budgets (budget §4): `steps` 100, `tokens` 2,000,000, `time` 2 h, `tool_calls`
  500. Default extensions: 50 steps, 500,000 tokens, 30 min, 200 tool calls. Only
  `actor=user` may extend.
- Loop reminder levels are exactly 3, 5 and 8 consecutive identical calls (continuation §4).
- Coverage of `internal/kernel` and `internal/execstore` ≥ 90 %; mutation threshold per
  quality gates; non-test files ≤ 500 lines, test files ≤ 800.
- Rejections use existing `RejectionCode` values where one fits; a new code is added to
  `rejection.go` and to `docs/error-codes.md`.
- The PR stays under roughly 600 changed lines excluding tests and testdata. If it will not,
  **stop and ask the user** before opening it; the natural split is Tasks 1–3 (after-step
  rules) and Tasks 4–6 (budgets, end, loop).
- Do not touch `internal/coordinator` (F2.6a is in progress there) or timer decisions
  (F2.6c).

## Scope decisions made by this plan

The reviewer may reject these.

1. **Precedence of the after-step rows** (continuation §2 lists them unordered):
   `stop_intent` > `refused` > `tool_terminate` > `truncated_args` > `tool_calls` >
   `steer_pending` > `truncated_continue` / `truncated_end` > `natural_end`. After the row is
   chosen, a decision to continue becomes `budget(steps)` when steps used reach the limit.
2. **Where each budget is checked** (budget §4.1, state-machine §9): `steps` when the step
   completes; `tokens` at `AdvanceRun`, before the next model plan (the step boundary);
   `tool_calls` before each `ToolDispatchStarted`. A `tool_calls` wait leaves the remaining
   tools of the step `Ready` or `Planned`; an extension resumes them in the same step.
3. **Counters.** `StepsUsed` counts `StepStarted`; `TokensUsed` sums
   `BudgetObserved.TokensUsed`, which the host already reports as new tokens only (cached
   input excluded, reasoning included); `ToolCallsDispatched` counts `ToolDispatchStarted`.
   The limit of a kind is the pinned value plus all `BudgetExtended` amounts of that kind.
4. **`truncated_continue` carries a context injection.** The step after it must receive
   `Facts.ContinuationPromptRef`; `planStep` emits `ContextInjected(source=truncated_continue)`
   in the same batch. The prompt text is the host's (F4.5).
5. **`time` is pinned but not enforced.** `RunAccepted` pins all four budgets; active-time
   windows, `run_deadline` and `budget(time)` belong to F3.4.

## Review Focus

1. **A `length` answer whose tool calls are cut** — none is dispatched, each gets a
   synthetic `truncated_args` failure before `StepCompleted`. Pinned in Task 3
   (`TestTruncatedToolCallsNeverDispatch`).
2. **The step budget reached by a step that still has tools running** — the tools finish
   first, then the run waits. Pinned in Task 4 (`TestStepBudgetWaitsAfterToolsFinish`).
3. **An extension by a non-user actor or for a kind that is not waiting** — rejected, nothing
   appended. Pinned in Task 4 (`TestOnlyUserExtendsBudget`,
   `TestExtensionForKindNotWaitingIsRejected`).
4. **A replayed run** — rebuilt state has the same counters, blocks and loop counter as the
   live one. Pinned in Task 6 (`TestBudgetWaitSurvivesStoreReopen`) and the rapid property in
   Task 4.
5. **A loop reminder that is due without a payload ref** — the batch is rejected rather than
   silently dropping the reminder. Pinned in Task 5 (`TestDueLoopReminderRequiresPayloadRef`).

### Task 4: Budget waits, extension and the minimal end

**Files:**
- Create: `internal/kernel/decide_budget.go`, `internal/kernel/decide_budget_test.go`
- Modify: `internal/kernel/{decide.go,decide_run.go,decide_tool.go}`, `internal/execstore/metadata.go`

**Interfaces:**
- Consumes: Tasks 1–3, `RunBlockAddedEvent`, `RunBlockClearedEvent`, `RunStopRequestedEvent`.
- Produces: `case *ExtendBudgetCommand` and `case *RequestStopCommand` in `decision.command`.
  - `steps`: when `AfterStep` returns `budget(steps)`, the batch is `StepCompleted(budget,
    steps)` + `RunBlockAdded(Kind=budget, BudgetKind=steps)`; no `RunFinished`.
  - `tokens`: `AdvanceRun` with `TokensUsed ≥ limit` emits only
    `RunBlockAdded(budget, tokens)`.
  - `tool_calls`: `PrepareDispatch` on a `Ready` tool with `ToolCallsDispatched ≥ limit`
    emits only `RunBlockAdded(budget, tool_calls)`.
  - `ExtendBudget`: requires `Actor == "user"`, `ExtensionAmount > 0` and an open block of
    that kind; emits `BudgetExtended` + `RunBlockCleared` for that block. Otherwise a
    rejection and no events.
  - `RequestStop` (Q-17): accepted only for `Reason=budget`, `Mode=terminal`,
    `Actor=user`, an open budget block and no active attempt; emits `RunStopRequested` +
    `RunFinished(budget_exceeded)` whose `PrimaryStopRef` is the stop event. Any other stop
    returns `RejectionCodeUnrecognizedCommand` as today.
  - `execstore/metadata.go`: `ExtendBudget` allows `Kind`, `ExtensionAmount`, `Actor`;
    `RequestStop` additionally allows `Actor`.
