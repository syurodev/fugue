# F9.9 — Vendor session service over the Host API

**Goal:** expose Claude vendor sessions and their transcripts over the versioned Host API while preserving the vendor runtime's single-writer, recovery, vault, and content-protection rules.

**Architecture:** Keep vendor lifecycle transitions in a pure state machine in `internal/vendor`. A per-session actor is the sole writer to `internal/vendorstore`; it consumes Claude observations, records events and transcript items, and publishes through the transcript composition from F9.4b. `internal/app` owns services and command deduplication, while `internal/hostapi` maps Connect requests and responses. `fugue.vendor.v1` owns vendor operations and `fugue.transcript.v1` owns transcript reads; existing transcript topics remain the streaming path.

**Scope:** Claude only. Codex and agy return a typed unsupported error until their adapters are implemented. No production code is part of this planning PR.

**References:** base-doc `vendor-runtime` §§6, 7, 9–11, 13, 15; `transcript` §§5–6; `host-api` §§4–7 and §5.1; vendor-session relay in `vendor-runtime` VR-05; `docs/roadmap.md` F9.3–F9.6 and F9.9; current `internal/vendor`, `internal/vendoradapter/claude`, `internal/vendorstore`, `internal/transcript`, F9.4b `internal/app` transcript composition, and F5.3a interaction service/Connect handler.

## Contracts and boundaries

### State machine and session actor

- Add a deterministic state machine to `internal/vendor` for `starting`, `ready`, `running`, `awaiting_approval`, `waiting(reason)`, `detached`, and `closed`, and turn outcomes `completed`, `interrupted`, `failed(code)`, and `unknown`. Transitions accept facts and return next state/effects; they read no clock, do no I/O, and own no goroutines.
- Create one supervised actor per live session. It is the only application component allowed to append that session's events or items to `vendorstore`. The actor serializes commands, adapter observations, vault notifications, and close/recovery facts; failed appends do not advance its in-memory sequence.
- Consume `(*claude.Session).Observations()` as a bounded 256-entry channel (Q-44); backpressure is intentional. Convert each observation to the existing vendorstore event/item model. Persist durable observations before publishing them. Record content and raw vendor payload only through vendorstore's protected payload path; keep free text out of event metadata, errors, and logs.
- The F9.5b normalizer may emit a `TurnEnd` and items for a vendor-initiated `vendor-<uuid>` turn after a late steer, including `late_steer` and `absorbed_into_vendor_turn` notices. Persist a separate `vendor_turns` row with `origin = vendor`; do not attach it to the nearest Fugue turn. Add an additive vendorstore migration with `origin TEXT NOT NULL DEFAULT 'fugue' CHECK(origin IN ('fugue','vendor'))`, so existing and new Fugue turn rows retain `origin = fugue`. This preserves the vendor's actual turn boundary and lets items satisfy the existing `(session_id, turn_id)` foreign key without corrupting Fugue turn outcomes. Add the event field, projection and validation in F9.9a. The session state machine records the vendor turn but does not transition the session to `running` because of that turn; only a Fugue `Send` owns that control-state transition. For an absorbed send, the actor persists vendor-origin items/notices on the `vendor-<uuid>` row, but applies the matching `TurnEnd` to the active Fugue turn and returns the session to `ready`.
- Reuse F9.4b `app.Transcripts` for `transcript:<session>` and `transcript-delta:<session>`. Durable item commits publish only after storage commits. Partial observations update the in-memory coalescer; they are not durable transcript events. Existing snapshot/catch-up behavior and vault-aware redaction remain authoritative.
- Transcript views preserve the separate turn IDs and expose `origin = vendor` in the item's allowlisted metadata; the UI renders these as vendor-origin timeline groups with their notices and items, visibly distinct from user-started Fugue turns. The `absorbed_into_vendor_turn` notice remains attached to the Fugue send that was absorbed, while the vendor-generated content stays on its vendor-origin turn.
- On vault lock or unknown vault state, stop delta publication, interrupt an active turn, record the turn as interrupted when proven or unknown when not proven, then persist `waiting(vault_locked)`. Do not write protected payload while locked. Unlock permits a new turn; it does not replay the interrupted input.
- On process exit without a terminal observation, end an active turn as `unknown`; record the process exit and `StopProof` (`proved` or `unknown`) before closing the session. Never retry/replay a possibly-effectful turn automatically.
- Reuse `vendorstore.Store.Recover` at host startup: reap recorded process identities through the F9.2 process supervisor, preserve `StopProof`, mark open turns `unknown`, and leave recoverable sessions `detached`. Resume is an explicit new session-process action; the old turn is never continued implicitly.

### Host API and protobuf

- Add `proto/fugue/vendor/v1/vendor.proto` with `VendorService`: `ProbeVendors`, `StartSession`, `Send`, `Interrupt`, `Steer`, `CloseSession`, `ResumeSession`, and `ListSessions`.
- Add `proto/fugue/transcript/v1/transcript.proto` with `TranscriptService.TranscriptPage` and `TranscriptItem`, plus the public `TranscriptPage` and `TranscriptItem` message shapes. These are unary reads. Existing `transcript:<session>` and `transcript-delta:<session>` topics from F9.4b remain the stream surfaces and are not duplicated by new topics.
- Generate Go and TypeScript bindings with the repository's pinned Buf configuration. Run `task proto` against the configured breaking baseline before merge. Keep domain and application packages free of generated imports. Additive fields/RPCs are preferred; a breaking contract change requires an explicit migration path and review of the Buf `FILE` breaking check.
- Put application orchestration in `internal/app`; add Connect handlers and mount both services in `internal/hostapi`. Derive principal/origin from authenticated connection state, never from client fields. Keep authorization in the service layer as well as transport checks.
- State-changing requests carry `command_id`. Apply the F5.3a interaction-service pattern: bounded in-flight deduplication, concurrent same-ID singleflight, and replay the original result for a retry; reject reuse of an ID with a different canonical command as `invalid_argument`. Keep cache bounds/retention consistent with that service unless a Q decision changes the policy. Queries do not need a command ID.
- Publish stable public error codes in `internal/platform/errcode` and `docs/error-codes.md`; map typed errors to Connect codes/details using the existing `toConnectError` path. Minimum public distinctions: unsupported vendor/operation, session not found, invalid session state/busy turn, session capacity, vault locked, turn not active, stale/unknown command ID conflict, and transcript item not found. Internal process, storage, and secret details remain redacted.

### Session profiles and adapter inputs

- This phase exposes only Claude. `ProbeVendors` reports Claude's probe/version/capability/login result; a Codex or agy request fails with the typed unsupported-vendor result and does not create a store record or process.
- Use the existing validated `vendor.StartSpec` allowlist: `Model`, `Effort`, and `ResumeSessionID` map to Claude's already vetted argv. `StartSession` receives `Cwd` from the client because the user chooses the folder in the app; the host validates it before spawn under the Q-57 rules. Vendor home and account context remain host-side. Do not expose arbitrary argv, environment, permission-widening flags, or raw account credential material.
- Preserve vendor defaults unless an explicit supported opt-in profile is selected. F9.9 exposes `Model`, `Effort`, and `ResumeSessionID` directly, each validated by the existing Claude argv allowlist; other profile values remain host-side defaults (Q-53 A, decided by the owner). Invalid or unsupported options fail before spawn and do not appear in error text.
- Persist vendor session metadata and resume handle with `vendorstore`; never persist secrets. A resumed session is a newly spawned process attached to the vendor's resume handle, with a new Fugue turn identity and an explicit resume event/state transition.

### `/fugue:` commands

- Route exact recognized `/fugue:<name>` prompts in the host command dispatcher before calling `Session.Send`. A recognized host command is never sent to a vendor. A prompt beginning `/fugue:` but not matching a command registered for this phase is rejected with the typed invalid-command error; it is never passed to Claude.
- Keep the command field and dispatcher separate from vendor slash commands. Claude slash-command discovery continues to hide `terminal_slash_commands` and updates from `system/init` are represented as session observations.
- F9.9 implements only commands with a settled owner and behavior. `/fugue:team` and `/fugue:solo` require orchestration/team creation and belong to F11.2; `/fugue:account` requires account selection/login and belongs to F9.10. F9.9 records those dependencies and does not implement them. Reject any other `/fugue:` input before vendor dispatch (Q-54 A, decided by the owner).

### Limits and deadlines

- Before F11.6 scheduler support, cap at two active Claude processes per host and reject a new `StartSession` with a typed capacity error. `waiting(capacity)` is reserved for sessions explicitly queued by a later scheduler (Q-55 A, decided by the owner).
- Preserve the existing process-level limits: 30-second Claude handshake, 8 MiB JSON line, 64 KiB stderr ring, and 10-second protocol interrupt wait. RPC maxima are 35 seconds for probe/start/resume, 30 seconds for close, 12 seconds for interrupt, and 5 seconds for other unary calls; transcript pages default to 200 and cap at 500 (Q-56 A, decided by the owner).
- `Process.Stop(ctx)` kills the process tree immediately when `ctx` is already canceled, bypassing the F9.2 escalation order. Therefore `CloseSession`, interrupt escalation, and `StartSession` cleanup run stop operations with a detached context (`context.WithoutCancel` or the actor's independent lifecycle context) and always complete the F9.2 stop order. The RPC deadline limits only how long the caller waits: on expiration, return the current operation state (for example `closing` or `interrupting`), while the operation continues.
- `Session.Interrupt` waits at most 10 seconds for the protocol interrupt and then escalates through `Close`; that stop sequence may take about 21 seconds. The `Interrupt` RPC returns when its own wait deadline expires, and the final outcome is published through the session topic. `CloseSession`, `Interrupt` escalation, and `StartSession` cleanup must not inherit a canceled RPC context. A retry with the same `command_id` attaches to the in-flight operation instead of starting another stop/cleanup (Q-56 A, decided by the owner).
- Enforce the above with `TestCloseRPCDeadlineDoesNotSkipStopOrder`, `TestInterruptRPCDeadlineLetsEscalationFinish`, and `TestRetrySameCommandIDAttachesToInFlightClose`.
- Transcript page defaults to 200 items, newest first; cursor is the item's creation sequence and updates do not move it. `TranscriptItem` returns latest revision. While vault locked or state is unknown, return metadata with `content_locked`; do not return protected content or deltas.

## Decision record and open questions

Q-53–Q-58 are decided by the owner and recorded in `docs/roadmap.md`.

### Q-53 — Which session profile fields are client-selectable in F9.9?

- **A (recommended):** expose the supported `Model`, `Effort`, and `ResumeSessionID` fields directly, each validated by the existing Claude argv allowlist; all other profile values remain host-side defaults.
- **B:** expose a small named profile enum and resolve all model/effort options on the host.
- **C:** expose the full vendor-runtime §7 profile surface now, rejecting any option without a verified Claude flag.

**Recommendation:** A. **Answer:** A decided by the owner.

### Q-54 — Which executable `/fugue:` commands belong to F9.9?

- **A (recommended):** F9.9 implements only commands with a settled owner and behavior; `/fugue:team` and `/fugue:solo` stay with F11.2, `/fugue:account` stays with F9.10, and F9.9 still rejects unknown `/fugue:` input before vendor dispatch.
- **B:** include `team`, `solo`, and `account` as placeholders in F9.9, returning typed unavailable until their owning services land.
- **C:** move those command implementations into F9.9 and make F11.2/F9.10 depend on the service.

**Recommendation:** A. **Answer:** A decided by the owner.

### Q-55 — What is the pre-scheduler concurrent session limit and capacity behavior?

- **A (recommended):** cap at two active Claude processes per host; reject a new `StartSession` with a typed capacity error, and persist `waiting(capacity)` only for an already-created session that is explicitly queued by a later scheduler.
- **B:** allow one active process per host and return the same typed capacity error.
- **C:** allow a larger fixed cap (owner supplies the value) and queue excess sessions as `waiting(capacity)` now.

**Recommendation:** A. **Answer:** A decided by the owner.

### Q-56 — What RPC deadlines and page-size ceiling should F9.9 publish?

- **A (recommended):** set explicit service defaults: 35 seconds for probe/start/resume (30-second handshake plus margin), 30 seconds for close (covers the F9.2 stop sequence), 12 seconds for interrupt (10-second protocol wait plus margin), 5 seconds for other unary calls, and transcript page size default 200 / maximum 500; caller deadlines may shorten but not extend host maxima.
- **B:** require caller deadlines only and use existing process timeouts for internal waits; maximum transcript page 200.
- **C:** choose longer values and page maximum with the desktop client after profiling.

**Recommendation:** A. **Answer:** A decided by the owner, with the cancellation rule of plan §Limits: CloseSession, Interrupt escalation and StartSession cleanup run detached from the RPC context and always complete the F9.2 stop order; a retry with the same `command_id` attaches to the in-flight operation.

### Q-57 — What working directory may StartSession use before F5.6?

- **A (recommended):** accept the user's app-selected `cwd` from the client; require an absolute, existing directory; resolve the real path with `EvalSymlinks`; reject the Fugue data directory or any path inside it, and reject `/`; when F5.6 workspace support lands, require `cwd` to be one of that workspace's roots.
- **B:** let the client select only from a list of directories configured on the host.

**Recommendation:** A. The app's user-selected folder is the session's working context under VR-06; host validation still controls what reaches process spawn. **Answer:** A decided by the owner, with one addition: the `cwd` must also not be the Fugue home directory (`~/Fugue`, Q-60 of the F5.6 plan) or any path inside it, so a vendor session never runs where Fugue configuration lives.

### Q-58 — How does the app learn that the session list changed?

- **A (recommended):** add durable topic `vendor-sessions` in F9.9b with a snapshot of sessions and their states, plus events when a session is created or changes state. F10.4 uses `ListSessions` for initial state and subscribes for live updates.
- **B:** have F10.4 poll `ListSessions` and add no session-list topic in F9.9.

**Recommendation:** A. It gives F10.4 the same reconnect and catch-up behavior as the existing session transcript topics; B adds periodic requests and delays updates between polls. **Answer:** A decided by the owner: durable `vendor-sessions` topic in F9.9b; F10.4 reads `ListSessions` first and then subscribes.
